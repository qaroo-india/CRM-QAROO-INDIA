# Deployment

The recommended production setup is **Vercel** for the web app and **Render** for the
API. It uses the `vercel.json` and `render.yaml` at the repository root.

```
 Browser ──HTTPS──▶ Vercel  (client/dist, static)
                      │  /api/*  rewrite (server-side proxy)
                      └────────────HTTPS────────────▶ Render web service (Express)
                                                         └─ /var/data  persistent disk
                                                              ├─ institute.db   (SQLite)
                                                              ├─ storage/       (documents, report files)
                                                              └─ backups/       (npm run db:backup:prod)
```

**Why the rewrite matters:**

- The browser only ever talks to your Vercel domain, so the auth cookies are first-party.
- The cookies are `HttpOnly; Secure; SameSite=Strict`. If the browser called the Render URL directly, those cookies would never be sent and every sign-in would fail.

> Nothing here has been deployed for you. Both platforms need your own accounts. These
> steps were checked locally:
>
> - the exact install and build commands from `vercel.json` and `render.yaml`, on a clean copy of the repository;
> - the production start sequence (`migrate → seed → serve`), with `NODE_ENV=production`.

---

## 1. Before you start

- [ ] Push the repository to GitHub (or GitLab/Bitbucket).
- [ ] Decide your domains. A Vercel subdomain (`your-app.vercel.app`) works.
- [ ] Get SMTP credentials if you want real email. Examples: Amazon SES, Brevo, Mailgun, Postmark, or Google Workspace SMTP relay. Without SMTP, set `EMAIL_TRANSPORT=disabled`; emails are then recorded as failed instead of being faked.
- [ ] Choose a strong **owner initial password** of 10+ characters. You change it at first sign-in.

## 2. API on Render

1. In the Render dashboard, choose **New → Blueprint** and select the repository. Render reads `render.yaml`.
2. Fill in the values marked *sync: false*:

| Variable | Value |
|---|---|
| `CLIENT_URL` | `https://your-app.vercel.app` (comma-separate several origins) |
| `APP_URL` | the same URL; used for links in emails |
| `OWNER_EMAIL`, `OWNER_NAME`, `OWNER_INITIAL_PASSWORD` | the first owner account, created on first start |
| `INSTITUTE_NAME` | shown on receipts and reports (editable later in Settings) |
| `SMTP_HOST`, `SMTP_USER`, `SMTP_PASSWORD`, `EMAIL_FROM` | your mail provider (or set `EMAIL_TRANSPORT=disabled`) |

3. Leave the rest as the blueprint sets them:
   - `JWT_ACCESS_SECRET` is **generated by Render**.
   - `DATABASE_URL=/var/data/institute.db`.
   - `STORAGE_DIR=/var/data/storage`.
   - `HOST=0.0.0.0`.
   - `TRUST_PROXY=2`.
4. Deploy. The start command runs `migrate → seed → server`. All three steps are safe to repeat on every deploy.
5. Check `https://<service>.onrender.com/api/v1/health`. It should report `"status":"ok"`.

**Important facts about the Render setup:**

- **A persistent disk is required.** SQLite is a file. On an instance without a disk, every deploy or restart erases the database. Disks need a paid instance type; the blueprint uses `starter`.
- **One instance only.** SQLite has a single writer, and the scheduler that sends report emails must not run twice. Disk-backed services also have no zero-downtime deploys, so there are a few seconds of downtime per deploy.
- The server refuses to start in production if:
  - the JWT secret or owner password is a development default;
  - `EMAIL_TRANSPORT=log`;
  - the database is in-memory;
  - a `CLIENT_URL` is plain `http://`.

  The log names the variable.

## 3. Web app on Vercel

1. In `vercel.json`, replace `REPLACE-WITH-YOUR-RENDER-SERVICE` with your Render service name, then commit.
2. In Vercel, choose **Add New → Project** and import the repository.
   - Keep the **root directory as the repository root**; `vercel.json` sets the install, build and output commands.
   - Framework preset: *Other*.
3. Environment variables: none are needed. `VITE_API_URL` defaults to `/api/v1`, which goes through the rewrite.
4. Deploy, open the site and sign in with `OWNER_EMAIL` and `OWNER_INITIAL_PASSWORD`. You are asked to set a new password.

`vercel.json` also sets security headers for the app:

- **Content-Security-Policy:** only one inline script is allowed, by its hash. `client/src/test/csp.test.ts` fails if `client/index.html` changes without updating the hash.
- HSTS, `X-Frame-Options: DENY`, nosniff, a referrer policy and a permissions policy.
- Long-term caching for hashed assets.

## 4. After the first deploy

- [ ] Sign in as the owner and change the password (required).
- [ ] **Settings:** institute name, address, GSTIN, code prefixes, lead sources, expense categories, report recipients.
- [ ] **Staff & permissions:** create staff accounts. Grant `reports:financial`, `payments:refund`, `documents:restricted` and the other permissions deliberately.
- [ ] **Reports → Email:** send yourself a report. History shows `sent`, and the email arrives with the attachment.
- [ ] **Reports → Schedules:** add the daily/weekly/monthly reports the owners want.
- [ ] Set up backups (below) and do one restore drill.

## 5. Backups

Use both of these. A backup on the same disk does not survive losing the disk.

**a) Snapshot copies.** These are consistent online copies made with SQLite's backup API, so they are safe while the server writes.

```bash
npm run db:backup                      # development
npm run db:backup:prod --workspace=server   # production (Render shell), uses dist/backup.js
```

Each run writes `<db folder>/backups/institute-YYYYMMDD-HHMMSS.db`, verifies it with an integrity check, and keeps the newest 30 (`--keep=N` changes that).

- On Render, run it from a **Cron Job** service, or from the shell before risky changes.
- **Copy the files off the server** regularly, for example by downloading them or syncing them to object storage.

**b) Continuous replication: [Litestream](https://litestream.io).** This streams every change to S3-compatible storage (AWS S3, Backblaze B2, Cloudflare R2), so you lose at most seconds.

1. Add a `litestream.yml`:

   ```yaml
   dbs:
     - path: /var/data/institute.db
       replicas:
         - url: s3://YOUR-BUCKET/institute
   ```

2. Change the start command to `litestream replicate -exec "npm run start:prod --workspace=server"`. This needs Litestream installed in the build, or a Docker deploy.
3. Keep the bucket credentials in Render environment variables, never in the repository.

**Restore drill** (do it once before relying on a backup):

1. Stop the service.
2. Copy a backup (or run `litestream restore`) to `/var/data/institute.db`.
3. Delete any stale `institute.db-wal` and `institute.db-shm`.
4. Start the service.
5. Check `/api/v1/health` and a known receipt.

Documents and report files live in `/var/data/storage`. Back up that folder too; a disk snapshot covers both.

## 6. Alternatives

- **Turso (hosted libSQL)** instead of a disk: the data layer is written so that only `server/src/db/index.ts` changes (the driver). This is not built yet; see [ARCHITECTURE.md](ARCHITECTURE.md) §1.
- **Postgres:** rewrite `server/src/db/dialect.ts` and the driver, then regenerate migrations. The services and tables stay the same.
- **Docker / a VPS:** `npm ci && npm run build`, then run `npm run start:prod --workspace=server` with the same environment variables. Put a TLS reverse proxy in front, serve `client/dist` from the same domain, and proxy `/api` to the API. Set `TRUST_PROXY` to the number of proxies.

## 7. Troubleshooting production

| Symptom | Cause and fix |
|---|---|
| Sign-in "succeeds" but you are immediately signed out | The browser is calling the API on another domain, so `SameSite=Strict` cookies are dropped. Use the Vercel rewrite and keep `VITE_API_URL=/api/v1`. |
| `403 CSRF_FAILED` on every save | Same cause as above, or a stale tab after a deploy. Reload the page. |
| CORS error in the console | `CLIENT_URL` on Render must exactly match the site origin: scheme and host, with no trailing slash. |
| Everyone gets "Too many requests" together | `TRUST_PROXY` is too low, so all users share the proxy's IP. It is 2 behind Vercel + Render, and 1 if browsers call Render directly. |
| Data vanished after a deploy | No persistent disk, or `DATABASE_URL` is not under the disk's mount path. Restore from backup and fix the blueprint. |
| Report emails show `failed` | Open Reports → History: the provider's error is shown, for example authentication or a sender domain that isn't verified. Fix SMTP_*, then use **Retry**. |
| Emails show "not delivered (dev mode)" | `EMAIL_TRANSPORT=log` is a development-only setting; production refuses to start with it. |
| Health shows `migrations: degraded` | A deploy didn't run migrations. The start command does this; check that it is `npm run start:prod --workspace=server`. |
